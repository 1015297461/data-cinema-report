# Data Cinema 报告陷阱清单（实战踩坑，生成与自检时逐条对照）

本清单来自多轮真实返工，每条都是**曾经出错并被用户指出**的问题。生成后按「自检命令」段落逐条跑一遍。

## A. 数据摄取层

**A1 Excel 列偏移——表头必须逐列核对，不能按列数推算**
- 症状：销量/销售额整体翻倍或错位。
- 原因：表头月份列数量与预期不符时（如实际 24 个月却按 25 列切片），把销售额首列当成了销量末列。
- 做法：先打印 `hdr[0:N]` 与首行数据对齐核对，确认「销量起止列」「销售额起止列」「月份顺序（升序/降序）」三件事再计算。
- 尤其注意：源表常是**降序月份**（2026-09 → 2024-09），做趋势图前必须 `reversed()`。

**A2 标签数组与数据数组错位**
- 症状：横坐标写 8月~7月，数据却是 1~12 月顺序，每个月显示的都是别的月的值。
- 做法：标签数组与数值数组必须来自**同一次排序**；改排序时两个一起改，或干脆用 `{月: 值}` 字典映射后再排序输出。

**A3 财年切法不直观**
- 用户明确否定「2024-08~2025-07 vs 2025-08~2026-07」双年对比。
- 季节性一律：**自然月 1~12 排列 + 单年度柱状 + 全年月均金色虚线**，峰值月/谷值月用颜色区分（峰=coral，谷=rose，其余=cyan）。同比结论写进 insight 文字，不塞进图里。

## B. HTML 结构层

**B1 字符串替换丢闭合标签 → 卡片外框残缺**
- 症状：某张卡片的白色圆角边框"缺一块"，与相邻卡片粘连。
- 原因：用 `body.replace(旧文案, 新文案)` 改 insight/src 文字时，新字符串末尾漏了 `</div>`。
- 强制自检：构建后跑 `len(re.findall(r'<div\b', html)) == html.count('</div>')`，不等就报错中止。

**B2 Python 拼 `</script>` 写成字面量 → 整页空白**
- 症状：截图全白，什么都没了。
- 原因：在 Python 三引号字符串里写 `'</' + 'script>'`，拼接表达式被当字面量写进文件，script 永不闭合，后续整个 body 被吞。
- 做法：用 `chr(60) + '/script' + chr(62)` 或先把闭合标签存变量再拼接；构建后断言 `<script` 与 `</script>` 数量相等。

**B3 路径解析误匹配**
- `glob('cls_parts/part*.txt')` 配 `p.split('part')[1]` 会命中目录名 `parts` 里的 `part`，抛 `ValueError: invalid literal for int()`。
- 做法：排序键用 `re.search(r'part(\d+)\.txt$', p)`，别用 split。

## C. 布局与视觉层

**C1 入场动画 translateY 大于卡片间距 → 模块重叠**
- 症状：用户报「每个模块的外框没有独立显示，重叠到一起」。
- 原因：`.reveal{transform:translateY(28px)}` 而卡片 `mb-6` 只有 24px，动画过程中卡片下移压叠下一张。
- 做法：**入场动画只用 opacity 淡入，不做位移**（模板已改）。若一定要位移，必须 `translateY < 卡片间距`。

**C2 相邻卡片无间距（尤其"在末卡后再追加一张"时）**
- 症状：两张卡片白框紧贴、中间 0 间距（典型如 2.5 表格卡与 2.6 图表卡粘连）。
- 根因：规范是「同一 section 内除**最后一张**卡片外都要 `mb-6`」。当你往章节**末尾追加新卡片**时，原来的末卡（当初按"末卡"写的 `class="card p-6 reveal"`，**没有** `mb-6`）就变成了中间卡，必须补上 `mb-6`；否则新末卡与它贴合。这是追加卡片时最容易漏的一步。
- 做法：追加卡片后，把**上一张末卡**的 class 改成 `card p-6 reveal mb-6`，新末卡保持无 `mb-6`。
- 构建期强制自检（务必内置到 build 脚本，扫描 body/成品 HTML）：
```python
import re
for si,s in enumerate(re.split(r'(?=<section)', body)):
    if '<section' not in s: continue
    cards=re.findall(r'<div class="card p-6 reveal( mb-6)?">', s)  # group='' 或 ' mb-6'
    titles=re.findall(r'<h3 class="font-bold mb-1 text-lg">([^<]+)', s)
    n=len(cards)
    for i,mb in enumerate(cards):
        assert not (i<n-1 and not mb), f"缺间距: 第{si}节 卡片 {titles[i].strip()}"
```
- 推广：任何"在章节内增删/重排卡片"的改动后都要重跑此审计，因为末卡身份会随之改变。

**C3 长轴名与刻度/图例重叠**
- 症状：`yAxis.name` 写成「ABA排名(小=好)」「月销量(件·对数轴)」这类长文本，与顶部刻度或图例撞在一起。
- 做法：**轴含义写进图表标题（h3）**，`yAxis.name` 只留极简（如"月销量(件)"）或省略。

**C4 对数轴折线不要加 areaStyle**
- `type:'log'` 折线加面积填充会渲染异常。对数轴图一律纯折线。

**C5 英文数量级缩写（12.25M / 20k）—— 中文报告严禁**
- 用户明确指出：报告中不得出现 `12.25M`、`20k`、`$9.02M` 这类英文数量级表达，必须改为中文「万 / 亿」。
- 做法：统一用模板内置的 `fmtCN(v)` —— ≥1亿 → `2.75亿`；≥1万 → `61.7万`；<1万 → 千分位原值。轴标签 / tooltip / label / 正文数字全部走它（`fmtM`、`fmtK` 已改为它的兼容别名，输出同为中文）。
- 金额保留 `$` 符号、数量级仍用中文：`$902 万`、`$2.75 亿`。
- 百分比 / 倍数 / 小数值不受影响：`+18.3%`、`19.8×`、`3,808 件`。
- 构建期硬断言（已内置 build_report.py）：`re.findall(r'(?<![A-Za-z])[\$]?\d+(?:[.,]\d+)?\s*[MK](?![A-Za-z])', body_src + charts_src)` 必须为空，否则中止构建。

**C6 x 轴类别标签是长中文名、且个数 ≥8 → 必须倾斜 + 放大底部留白**
- 症状：9 个二级分类名（带 `B1`~`B9` 前缀，最长 13 个全宽字符）摊在 category 轴上，`rotate:0` 必然横向重叠；`bottom` 若沿用短标签图的值（如 56）会把标签切掉。
- 估算公式（卡片内容宽约 1100px，`max-w-6xl` = 72rem 减 padding，9 槽约 122px/个；中文全宽字符宽 ≈ 字号 px）：
  - 水平投影 = `字数 × 字号 × cos(角度)` ≤ 槽宽 → 13 × 10 × cos40° ≈ 100px < 122px ✓
  - 平铺则 13 × 10 × cos0° = 130px > 122px ✗
- 垂直占用 = `字数 × 字号 × sin(角度)` ≈ 84px → `grid.bottom` 至少给 **100**（`containLabel:true` 时标签落在 grid 内部）。
- 参考值：3 个短标签 → `bottom:56`；9 个 13 字标签 → `rotate:40, bottom:104`。
- 缩短标签（去掉编号前缀）是下策——会与同章其他图（treemap / legend 都用 `f.name`）命名不一致。**优先保一致性，靠参数解决**。

**C7 三轴图（一个柱 + 两条量纲不同的线）的轴位与留白**

- 场景：同一张图要表达三个量纲互不相容的指标。实测 B3 部位图要同时放「近 12 月销量（4.5 万~95 万）」「均价（$11.66~$42.34）」「ASIN 月均销量（249~975）」——数量级相差百倍，塞不进两个轴。
- 做法：
  1. 柱用左轴（`yAxis[0]`，不写 position）；
  2. 两条线都放右侧，**靠 `offset` 拉开**：第一条 `position:'right',offset:0`，第二条 `position:'right',offset:74` —— 不设 offset 两个右轴的刻度会叠在一起；
  3. `grid.right` 同步放大（本例 76 → 158），否则右侧轴名被裁掉；
  4. **两条线用不同线型区分**（实线 / 虚线），不只靠颜色；标签位置也错开（一条 `position:'top'`、一条 `'bottom'`），否则 7 个 x 位置上 6 组标签会互相压；
  5. 三轴图**必须配自定义 tooltip**（`trigger:'axis'`，逐项列出三个值）—— 否则读者无法同时读到全部指标，且默认 tooltip 本身违反规范。
- **⚠️ 校验断言必须限定在单个 `mk()` 块内**：实测写 `assert src.count("position:'right'")==2` 会**误报失败** —— 全文件还有其他图用同名配置（实际 3 处，本图 2 处）。正确写法先切片：
  ```python
  A = src.index("mk('ch23'"); blk = src[A:src.index('})();', A)]
  assert blk.count("position:'right'") == 2 and re.search(r"offset:[1-9]", blk)
  ```
  同类陷阱：`legend:` / `tooltip:` / `grid:` / `label:` 这些键几乎每张图都有。**凡是要统计"某张图是否配了 X"，都必须先切块再数**。

**C8 x 轴 `name` 默认在轴右端，会被 `grid.right` 截掉**

- 症状：x 轴名右侧显示不全（被画布裁掉），但控制台无报错、静态自检也查不出。
- 根因：`xAxis.name` 默认 `nameLocation:'end'` —— ECharts 把它放在**轴的右端**，且用 `text-anchor="start"`（**从右边缘向右延伸**）。所以需要的是 `grid.right ≥ 文字完整宽度`，而不是一半宽度。实测：ch13 的「销量同比(%)」被渲染在 x=947、宽约 70px，画布 976px → **右缘 1016，裁掉 40px**。
- 修法（推荐）：把轴名移到轴线正下方居中，并同步加大底部留白：
  ```js
  grid:{left:10,right:44,top:34,bottom:76,containLabel:true},
  xAxis:{type:'value',name:'销量同比(%)',nameLocation:'middle',nameGap:34,...}
  ```
  `nameLocation:'middle'` 让名字落在轴线下方居中（`text-anchor="middle"`），既不占横向空间也不会被裁。
  ⚠️ `nameGap` 是相对**轴线**的距离，而且 `containLabel:true` **不包含 axis name** —— 所以 `grid.bottom` 必须手动预留。实测 34px 的 gap + 约 20px 刻度标签，把 `bottom` 从 56 提到 76 后：name 落在 y=358、刻度标签在 y=332，**间隔 26px 不重叠**。
- 备选修法：保持 `end`，把 `grid.right` 提到 110+ —— 但会挤压绘图区，且轴名跑到角落不美观。
- **同一份报告里 x 轴名的位置要统一**（都用 `middle` 或都不用），混用会让相邻图看起来不一致。

**校验方法：用 ECharts SSR 渲染做「零截图」布局验证**

不用浏览器、不截图，就能精确判断"到底哪个文字元素越界了"：

```python
# 1) 剥掉 echarts.inline.js 的 <script> 外壳（skill 自带资产是 HTML 片段，不是纯 JS）
src = open(".../assets/echarts.inline.js", encoding="utf-8").read().strip()
if src.startswith("<script>"): src = src[len("<script>"):]
if src.rstrip().endswith("</script>"): src = src.rstrip()[:-len("</script>")]
open("/tmp/_echarts.js","w",encoding="utf-8").write(src)
```
```js
// 2) Node 里 SSR 渲染 + 检查每个 <text> 的坐标（echarts 5.5 支持 ssr:true）
const echarts = require('/tmp/_echarts.js');
const ch = echarts.init(null, null, {renderer:'svg', ssr:true, width:976, height:420});
ch.setOption(cfg);
const svg = ch.renderToSVGString();
// 抓 <text> 的 transform / text-anchor / font-size
// 按 anchor 算左右边界：start → [x, x+w]；middle → [x-w/2, x+w/2]；end → [x-w, x]
// 文字宽度估算：中文 12px/字、其他 7px/字（fontSize 12 基准，按 font-size 比例缩放）

```
- 画布宽度要取**实际渲染宽度**：报告容器 `max-w-6xl`(1152) − `md:px-16`(128) − `card p-6`(48) ≈ **976px**，不要直接写 1024。
- 建议同时跑 **976 / 1024 / 640** 三个宽度，确认窄屏也不越界。
- **⚠️ 坑：不要用 `JSON.parse(JSON.stringify(series))` 做配置隔离** —— 它会**丢掉函数**（`label.formatter`、`tooltip.formatter`），ECharts 退回默认格式化，把 `value` 原样打印成一个长小数（实测渲染出并不存在的文本 `-10.98339532388154`，差点当成真 bug 排查）。要做隔离就重建配置对象，或直接复用同一份。

**C9 在对数轴上画柱状图（跨量级的主体对比）**

- 场景：同一张图要把「销量（件）」和「销售额（$）」两个维度、A/B 两个主体放进 24 个月，四组数据跨 **4,142 倍**。
- **先做"能否共轴"的判定，别急着画**：
  - 若把两个不同单位的序列放在**同一根轴**上会出事——实测 A 销量最大值（15.6 万件）**小于** B 销售额最小值（$1,864 万），但 A 的销售额（对数区间 4.95~6.38）与 B 的销量（5.91~6.09）**区间重叠**。共轴会让"$"和"件"在视觉上等高，读者必然误读。→ **不同量纲一律分轴**。
  - 两组主体差 100 倍以上时，**线性轴必死**（小的那组只剩几个像素），只能用对数轴。
- 做法（实际采用）：**双对数轴**
  ```js
  yAxis:[
    {type:'log',min:3000,max:2000000,     name:'销量(件·对数轴)', ...},   // 左轴：线
    {type:'log',min:50000,max:40000000,   name:'销售额($·对数轴)',position:'right',
     splitLine:{show:false}, axisLabel:{formatter:v=>'$'+fmtK(v)}}],      // 右轴：柱
  series:[ 柱(yAxisIndex:1, z:1) …, 线(yAxisIndex:0, z:10) … ]            // 柱在底层、线在上层
  ```
  - 右轴范围要**同时覆盖两个主体**（本例 $8.9万~$2,797万 → 取 5万~4000万），否则大的一方顶格截断、小的一方贴底。
  - 右轴 `splitLine:{show:false}` —— 否则两条对数轴的网格线会诱导读者横向对照刻度（两轴刻度含义不同）。
  - 柱用 `opacity:.28`；**线放在柱之上**（z 序），保证趋势线不被柱遮住。
- **⚠️ 对数轴上柱高的语义要写进 `src`**：柱高表示"量级位置"而非数值比例（对数轴上 27 倍的差距只占轴高的 49%）。不写清楚，读者会按线性直觉估算倍数。
- **⚠️ 一个无法用配置解决的视觉问题**：若同一主体的"量"与"额"走势几乎平行（本例 A 的销量与销售额都是 23~27 倍放大），则无论怎么设两条轴的范围，**该主体的柱与线都会落在相近的高度区间而视觉重叠**——这是数据本身决定的，不是坐标轴配置问题。可选处理：① 靠"柱淡 + 线实"的形态差区分（本报告采用）；② 改成上下双图共享 x 轴；③ 柱只保留一个主体。**要在交付说明里主动讲清，别让读者以为是画错了。**

**SSR 验证柱状图几何时的坑**

- 想从 SSR 出的 SVG 里读柱子的高度，**不能直接用 `<path d="M x y L x y …">` 的前两个点算**：ECharts 的柱（带 `borderRadius`）路径是 `M 左上角 L 右上角(圆角弧) L 右下 L 左下 …`，**开头两点的 y 相同**，照此计算会得出"柱高 0"的假结论（实测踩过）。
- 正确做法：取路径里**所有 y 坐标的 min/max** 作为柱顶/柱底；或直接按轴范围手算期望值再与渲染结果对照（`y_px = 轴底 − log10(v/axisMin)/log10(axisMax/axisMin) × 轴高`）。
- 顺带：`<path … fill="#f97316" fill-opacity="0.28">` 的正则计数会比实际多 2 —— **图例的色块也带同样的 fill**。24 个月的柱会数出 26（24 柱 + 1 图例 icon × 该系列）。

**C10 想要「一行两个」的网格，别用 `md:grid-cols-2` —— 模板里这个选择器是坏的**

- 症状：给图表容器加 `class="grid md:grid-cols-2 gap-4"`（想把 4 张图排成 2×2），桌面端**仍然是每行一个**，4 张图竖排成 4 行。
- 根因：模板里「本地化 tailwind」那段 CSS 的**响应式类选择器未转义冒号**：

  ```css
  @media(min-width:768px){
    .md:px-16{padding-left:64px;padding-right:64px}
    .md:grid-cols-2{grid-template-columns:repeat(2,minmax(0,1fr))}
  }
  ```

  CSS 选择器里 `:` 必须写成 `\:`。写成 `.md:grid-cols-2` 会被解析为「类 `.md` 上的伪类 `grid-cols-2`」→ **整条规则无效、被浏览器丢弃**。于是容器里只剩有效的 `.grid{display:grid}`，却没有列定义 → 退化成单列。**不是 `grid` 没生效，是「列数」没生效。**
- **同一个 bug 还让所有 `md:px-16` 失效**：报告正文 section 的桌面左右内边距实际一直是 `px-6`（24px），而非 `md:px-16`（64px）。所以卡内可用宽度比按 `1152 − 128` 估算的要宽 —— 算图表画布宽时别按 64px 内边距算。
- 做法：**不要依赖 `md:` / `lg:` 前缀**，在正文自带的 `<style>`（涨红跌绿那块）里定义一个自足的类：

  ```css
  .ks-2col{display:grid;grid-template-columns:repeat(2,minmax(0,1fr));gap:16px}
  @media(max-width:860px){.ks-2col{grid-template-columns:1fr}}
  ```

  容器写 `<div class="ks-2col mt-4">`。**非响应式的类（`grid` / `gap-4` / `mt-4` / `p-6`）都是有效的，可以照常混用**，只有 `md:` / `lg:` 前缀的失效。
- 若要在技能层面根治：把 `assets/template.html` 的 `@media` 块内 `.md:` / `.lg:` 统一转义为 `.md\:` / `.lg\:`。**注意这会真的启用 `md:px-16`（64px），所有既有报告的内容宽度都会收窄 ~80px** —— 属于可见版式变更，改前必须先跟用户确认，不要顺手改。
- **验证**：2×2 下单张图的真实画布宽 =（卡内宽 − gap）÷ 2。以 `max-w-6xl`(1152) + `px-6`(24×2) + 卡 `p-6`(24×2) 计 → 卡内 1056px，**单图约 520px**；SSR 布局检查要按 **≤520×360** 跑（保守取 480×360），**不能沿用整卡宽 976**，否则窄图里的轴名/轴标签越界会漏检。

**C11 同一量纲的双轴图，两轴必须设成完全相同的刻度 —— ECharts 会各自自动缩放**

- 症状：用户问「5.1 图里『该部位销量』和『术后场景销量』两个竖轴的值能不能做到等齐？」。看数据没错，看画出来的图却是错的——**柱顶和线点的相对高低与数值大小相反**。
- 根因：两个 y 轴都是 `type:'value'` 且只给了 formatter，**min/max 由 ECharts 各自按各自的 series 自动取整**。实测左轴自动取到 0~140 万（每格 20 万）、右轴只取到 0~120 万（每格 20 万）。于是「100 万」在左轴画在 `y=130`、在右轴画在 `y=94`。**同刻度不同比例 ⇒ 柱和线根本不能比**：膝的柱 106.7 万落在 y≈110.6，线 101.2 万落在 y≈100，**线反而画在柱顶上方**，读者会得出「术后场景比总销量还多」的错结论。
- 做法：**同一量纲（且希望读者做柱线对比）时，两轴显式写死相同的 `min` / `max` / `interval`**：

  ```js
  yAxis:[{type:'value',min:0,max:1400000,interval:200000,name:'该部位销量(件)',  …},
         {type:'value',min:0,max:1400000,interval:200000,position:'right',name:'术后场景销量(件)', …}]
  ```

  `max` 取两组数据的全局最大值再留一档余量（本例 max 1,209,442 → 取 140 万），并确认该值能容下**最高柱的数值标签**（标签在柱顶之上，留白不足会被裁）。**只靠 `splitNumber` 不保险**，显式 `interval` 才能保证两轴刻度逐条相同。
- 配套：**在 `src` 里写清「左右两轴同刻度」，并给出读法**（「线越贴近柱顶，比例越高」+ 两个点例，如 膝 95% / 头 14%），否则读者不知道这两个高度可比。h3 也加一句「左右两轴同刻度」。
- **别在 src 里写「两轴量级相近」来搪塞**：本例柱 120.9 万 vs 线 16.7 万（7 倍差距），原 src 写的「柱与线量级相近，故同为线性轴」本身就是错的。**下笔前先算一下两组数的 max/min 比。**
- 验证（零截图）：SSR 渲染后抓两轴的刻度文本，断言**左右刻度序列完全相同**；再抓柱标签与线标签的 `y`，断言「数值大的那个 y 更小（更靠上）」——这一步能直接抓出「线画到柱上面」这类错。
- 适用范围：只有**同一量纲**的双轴才需要同刻度。柱=销量 / 线=同比 这类异量纲组合**不要**同刻度（此时同刻度反而是错的）。

**C12 内容折叠（`<details>`）：长口径与附录默认收起 —— 但「摘要」与「展开内容」必须互斥**

**适用**：图下的「数据来源 / 口径」块、附录的整张卡（口径说明 / 公式表 / 明细表）。这类内容读者「需要时查、不需要时碍眼」，默认收起可把常显的密集小字降一个数量级（实测 3,584 → 390 字，−89%），而可追溯性不丢。

**结构范式**

```html
<details class="dc-fold srcd mt-2">
  <summary><span>数据来源：…（完整，不截断）</span><span class="dc-hint">口径与公式</span></summary>
  <div class="src">计算：① …；② …</div>
</details>
```

- `<summary>` 放**完整**的数据来源（一句话，不截断）＋右侧灰字提示（`margin-left:auto` 靠右）。
- 展开内容**以「计算：」开头**，只放算法与参数。
- 附录整卡折叠时，`<summary>` 里放**原来的 `<h3>` 本身**（HTML 规范允许 `summary` 内放一个 heading，`<h3>` 的计数与语义都不丢）：

```html
<details class="dc-fold apxd"><summary><h3 class="font-bold mb-1 text-lg">A.1 指标与公式速查表 <span class="src">(点击任意表头排序)</span></h3></summary>
  …原卡片内容…
</details>
```

**铁律：摘要与展开内容互斥。** 展开后看到「数据来源：X ｜ 数据来源：X ｜ 计算：…」是典型冗余（用户会直接指出「为什么解释了两次」）。
- 常见错法：`<summary>` 显示**截断**摘要（超 48 字加 `…`），展开内容再放**完整**原文 → 同一信息两套文本并存，且长条目要展开才能看到完整来源。
- 正确做法：**数据来源整段进 summary（不截断）、算法整段进展开内容**。摘要最长 73 字在 1056px 卡内仍是单行（11px 等宽下中文约 11px/字，ASCII 约 6.6px）。
- 判据（可直接写成构建门禁）：① 展开内容不以摘要开头、也不包含摘要；② 摘要不以 `…` 结尾；③ 展开内容以「计算：」开头。

**CSS（写在正文自带 `<style>`，不依赖 `md:` 前缀 —— 那个前缀在本模板里是坏的，见 C10）**

```css
details.dc-fold>summary{cursor:pointer;list-style:none;display:flex;align-items:baseline;gap:6px;flex-wrap:wrap}
details.dc-fold>summary::-webkit-details-marker{display:none}
details.dc-fold>summary::before{content:'▸';font-size:9px;color:var(--cyan);flex:0 0 auto}
details.dc-fold[open]>summary::before{content:'▾'}
details.srcd{margin-top:8px;font-family:'JetBrains Mono',monospace;font-size:11px;line-height:1.6;color:var(--sub)}
details.srcd>summary>span.dc-hint{font-size:10px;opacity:.7;margin-left:auto}
details.srcd>div.src{margin-top:6px;padding-left:12px;border-left:2px solid var(--line)}
details.apxd>summary>h3{display:inline;margin:0}

```

**打印兜底（必须做）**：折叠元素收起时**不会被打印**，导出 PDF 同样会丢。在报告主脚本末尾补（打印前全开、打印后还原）：

```js
window.addEventListener('beforeprint', () => { /* 全部 d.open = true */ });
window.addEventListener('afterprint',  () => { /* 还原原状态 */ });
```

**两个自伤坑**
1. **重建区块时手打标题文本**，会丢掉原标题里的内层元素（如 `<span class="src">(点击任意表头排序)</span>`）→ 必须**搬运原 `<h3>` 的 innerHTML**，不要手打。用「折叠前后逐条比对新旧纯文本」兜底。
2. **注释里写标签字面量**（CSS/JS 注释里写 `<details>`）→ 让产物的 `<details` 计数比 `</details>` 多 1，标签配平自检误报。注释里一律写「折叠元素」。

**验证（零截图）**：① 折叠块数量正确、且「默认展开数 = 0」；② 展开内容不以摘要开头、摘要不以 `…` 结尾；③ `<details` / `</details>` 配平；④ 语义元素（h3 数、表格 id 集合）与折叠前一致；⑤ **折叠前后 15 条 src 与附录三块内容逐字一致**（证明只改了呈现、没动内容）。

## D. 交互层（ECharts）

**D1 `tooltip.trigger:'axis'` 会绕过 series 悬停聚焦**
- 症状：配了 `emphasis:{focus:'series'}` 但悬停毫无反应。
- 原因：axis 触发接管了整个图表区的悬停（弹全系列数据面板），不再触发单条线的 emphasis。
- 做法：需要「悬停某条线→聚焦该线+只看它的数据」时，用**默认 item 触发**（不要覆盖 tooltip.trigger）。

**D2 主线 areaStyle 劫持全图悬停目标（最隐蔽的坑）**
- 症状：参考报告里效果正常，复制到新报告后"悬停任何位置都只聚焦同一条线"。
- 原因：参考报告的主线是**最下方**的线，面积块很薄；新报告主线是**最上方**的线，它的 areaStyle 覆盖整个绘图区，鼠标落在任何细线上实际命中的都是这块面积。
- 做法：**主线只在"位于图区底部/面积小"时才用 areaStyle**；否则一律不加，靠 `width:3 + symbolSize:6 + z:10` 区分主线。

**D3 blur 默认淡出不明显**
- 只写 `emphasis:{focus:'series'}` 时其余系列淡出很弱，用户会认为"没效果"。
- 必须显式：`blur:{lineStyle:{opacity:.08}, symbolSize:2}`，并给 emphasis 加粗 `lineStyle:{width: 原宽+2}`。

**D4 多系列配色数组长度要 ≥ 系列数**
- 症状：把 TOP6 扩到 TOP10 后，`lineStyle[6]` 为 undefined，颜色/宽度全崩。
- 做法：配色数组用 `pal.map((col,i)=>({color:col, width:i===0?3:1.8, z:10-i}))` 生成，或按 `i % pal.length` 取色，别硬编码 6 条。

**D5 图表 init 后再 `setOption({series: getOption().series})` 会吃掉坐标轴**
- 症状：散点/气泡图「横轴不见了」，纵轴或图例可能也在，极具迷惑性——同一 builder 里没这句的另一张图正常。
- 原因：拿 getOption() 处理后的 series 再 setOption 一次，等于局部覆盖重置了 axis 内部状态。
- 做法：mk/draw **一次成型**，绝不在初始化后回读再重设；双击还原用 `dispatchAction({type:'dataZoom',...})`，不要动 setOption。

**D6 气泡/散点图例色块与气泡不同色**
- 症状：legend 方块是默认调色盘色、气泡是自定义 alpha 色，对不上。
- 原因：legend 取 **series 级 `color`/`itemStyle.color`**；只在每个 data 项写 itemStyle、series 没顶层色时，图例回退默认。
- 做法：series 顶层设 `color:系列色`（不透明，供图例），data 项内再设 `itemStyle.color:系列色+透明度`（供气泡），两者同色。

**D7 单点极端值把气泡图压成一坨**
- 症状：四象限气泡「全挤在角落/一条线上」。
- 原因：某点小基数导致同比 +2000% 之类离群撑爆该轴；或半径按线性/单一除系数映射，量级差大时小点全叠一起。
- 做法：① 对超出稳健分位的轴值做**截断并在 tooltip 标「实际 X%，已截断」**（配 dataZoom 看全量），别让它决定轴域；② 半径用 **sqrt 按本图 min/max 归一到 10–52**；③ 同比类点先过「两窗口都有值 + 前窗口基数下限」，滤掉小基数伪高增长。

## E. 表格层
**E1 一个 ReferenceError 会静默杀掉后续所有渲染**
- 症状：某一张表空白，且它之后的所有表格/结论卡全部空白（图表因在表格之前定义所以还渲染，极具迷惑性）。
- 原因：用了未定义的格式化函数（如 `fnum`）。
- 做法：构建后断言脚本中引用的所有 `D.xxx` 键都存在；格式化函数集中定义在脚本顶部。

**E2 表头排序必须做数值解析**
- 直接按 textContent 排会把 `$9.80` 排在 `$19.32` 之后、`+113.9%` 按字符序乱排。
- 做法：`parseVal()` 剥掉 `$ % + − ,` 与 `K/M/万` 后缀换算成数值，`—`/空返回 `-Infinity` 沉底，非数值回落 `localeCompare(...,'zh')`。

**E3 明细表列名/口径**
- 多标签维度（节日/品种/颜色）份额加总会超 100%，必须在文末 APPENDIX · METHODOLOGY 口径说明与 src 行都写明"重复累积"口径。
- 中文翻译**并入英文名列**（`Wedding(婚礼)`），不单独开中文列。

**E4 模板脚本里的 `const` 存在 TDZ —— 图表代码必须插在 `const fpc` 之后（整页白屏级）**
- 症状：报告打开后**整页近乎全白**。HERO 大标题可见，但 KPI 卡片、所有图表区、结论卡全部不显示；浏览器控制台报 `ReferenceError: Cannot access 'fpc' before initialization`。
- 原因：模板主脚本里 `const fpc = ...`（表格百分比格式化器）声明在**靠后**位置（`fillTable` 之后）。若把图表配置插到它**之前**——例如插在 `/* 示例：横向正负条形涨跌榜 */` 这个示例块的位置——配置里对 `fpc()` 的调用会命中 TDZ（暂时性死区），脚本在该行中断；后续 `IntersectionObserver` 从未注册，`.reveal{opacity:0}` 永不解除，于是整页隐形。
- 做法：图表代码一律插在 `window.addEventListener('resize'` **之前**。此时 `const fpc` 已声明、IO 也已注册，即使图表代码再抛错，页面至少仍可读。
- 关键：`node --check` 与正则自检**都抓不到**（`fpc` 作为标识符语法完全合法），**必须做运行时检查**（见 F2）。

**E5 动态插入的 `.reveal` 元素不被已注册的 IntersectionObserver 观察 —— 整节「数据缺失」**
- 症状：某一节（典型是结论卡组 `#cards`）**整块空白**，但 DOM 里内容其实存在；页面其他部分正常。用户会描述为"XX 章节数据缺失"。
- 原因：`#cards` 的卡片是**脚本运行时**用 `innerHTML` 注入的，且带 `class="reveal"`；而模板的 IO 只在脚本里对**当时已存在**的 `.reveal` 做了一次 `querySelectorAll` + `observe`。后注入的元素不在观察列表 → 永远拿不到 `.in` → 永远 `opacity:0`。
- 高危区间：把图表/卡片渲染代码插到 IO 注册**之后**时必然触发 —— 修 E4（TDZ）时极易引入此回归。
- 做法（模板已内置）：IO 已暴露为可重入函数 `window.__observeReveal(root?)`；**任何动态插入 `.reveal` 的代码，末尾必须再调用一次** `window.__observeReveal()`。
- 自检：`runtime_check.js` 的 DOM 桩会解析 `innerHTML` 里的 `.reveal` 并投入元素池，最后断言「池中每个元素都曾 observe」，失败报「N 个动态注入的 .reveal 未被观察」。

**F4 图表容器必须写成 `<div id="chN" class="chart">`，属性顺序不能反**
- 症状：自检报「仅配置=['ch9']」，即配置了但找不到容器；页面上那张图空白。
- 原因：手写 body 时习惯性写成 `<div class="chart" id="ch9">`，而自检正则 `r'<div id="(ch\d+)"'` 只认 id 在前的写法。

**F5 模板残留的示例注释块会让自检误报**

- 做法：组装时两段都定位删除（用 `find('/* 明细表传第4参 true')` 找起点、`find('*/', k)+2` 找终点），别只删一段。

**F6 `SPL` 常量模板里没有定义**

- 做法：在注入的图表配置块**开头**显式 `const SPL='rgba(24,42,63,.08)';`。

**F7 insight 文案里的派生比例，必须单独算一次**
- 症状：正文写「单月已超过全年的三分之一」，实际是 28.5%；写「TOP50 占 78.2%」，实际 82.9%。
- 原因：只核对了聚合表里的**直接指标**，没核对文案里临时算出来的**派生比例**（占比、倍数、pp 差、峰谷比、象限计数）。
- 做法：落文案前把所有派生量单独 print 一遍；生成后再做一遍反向对账——把文案中每个关键数字用正则抓出来，逐个断言能在聚合结果里复算，不匹配即中止。

## G. 交付前内容自审清单（数字对了 ≠ 结论站得住）

> A–F 是**技术性**坑位（渲染、结构、数据摄取）。G 是**内容性**审查 —— 报告算得准、图也渲染正常，结论仍可能站不住。交付前逐条自问，任一不合格就不要交付。

**G1 分析对象是否属于同一可比范畴？**
- 把两类属性不同的商品放一起比"体量倍数"，读者会误以为同赛道。
- 做法：正文明确「主体 / 对照盘」，写清品类属性差异（如 B 含冷疗机等设备类、均价 $153），并声明"倍数仅用于判断量级，不构成同赛道竞争"。

**G2 样本筛选是否系统性剔除了高增长来源？**
- 为规避小基数而设的条件（如"上年度销量 < 200 则剔除"）常常正好把**新品**全剔掉。
- 实测案例：某报告剔除 91 个样本，其中 **55 个是全新品，贡献 13.3% 销量**；据此得出"增长靠头部拉动、不是普涨"，等于把这 13.3% 的高增长视而不见。
- 做法：必须披露被剔除样本的条数与销量占比；结论同时给"存量视角"与"含新品视角"。

**G3 重复计数是否只报了销量、漏报了条数？**
- 「同款不同色共享销量」这类问题，只算"销量多计 X%"不够 —— 均产、集中度、TOP N 占比全部以**条数**为分母。
- 做法：补报"唯一产品数"（实测：A 类 227 → 约 213 个、虚高 6.6%；B 类 1,295 → 约 1,171 个、虚高 9.6%），并点名哪些指标受影响。

**G4 同一个数字是否在两处承担不同含义？**
- 实测案例：KPI 卡写"峰谷倍差 17.4×"，正文写"1 月只有 17.4"（其实是季节指数）—— 数值撞车必然误读。
- 做法：全局搜关键数字，重复出现的逐个核对含义；不一致就换表述或加限定词。

**G5 术语是否精确？**
- 「谷值 ÷ 峰值」是季节性**振幅**，不是"抗跌性"；份额差 ≠ "溢价"（溢价看均价）。
- 做法：拿不准的术语换成描述性表述，不要套商业黑话。

**G6 趋势论断是否只有两个时点支撑？**
- 仅两个年度时点、且是跨品类比较，撑不起"增长在往 X 迁移"。→ 降级为"当期结构差异"，或补更多时点。

**G7 是否把"现象"直接说成"机会"？**
- "集中度低"既可能是机会，也可能是无序竞争 / 无品牌沉淀。→ 客观陈述指标，机会判断另行论证并给证据。

**G8 有无主观修饰词 / 未量化的程度词？**
- "**才**做出 28.1 万件"里的"才"、"仅"、"不过" —— 去掉，用数据说话。
- **更危险的是"小幅/略/显著/大幅"这类未量化的程度判断**：它们看似中性，实则在掩盖事实量级。
  实测案例：口径说明里写"新品会**小幅**推高分组同比"，复算后发现是 **15.5 个百分点**（剔除新品后 A 类同比从 +16.9% 掉到 +1.4%，即增长几乎全部来自新进入者）——"小幅"把一个关键结论写没了。
- 做法：凡出现程度副词，**强制替换为实测数字或占比**；替换时先跑一遍反事实计算（含 / 不含某类样本各是多少）。

**G9 中文报告是否混入英文数量级？**
- 禁止 `12.25M`、`20k`、`$9.02M`；构建期已有硬断言（见 C5）。

**G10 图表与正文口径是否一致？**
- 正文提"中位数"，但没说清是线性轴还是对数轴上的中位数 —— 两者数值差很多。→ 统一口径并注明。

**G11 章节 / 单图增删后，交叉引用是否全部同步？**

- 删掉**一整章**或**任意一张图**后，残留在**其他章节正文、结论卡「证据：」行、附录口径说明、页脚计数**里的引用会集体失效，且不会报错。
- 实测案例（单图版）：删掉「头部 20 名 vs 其余同比差」这张图后，结论卡里仍在引用它的 `+67.1% / −42.3% / 109.4pp`；删掉 B 类 TOP 50 表后，附录口径里仍写着「TOP 50 占比」。整章删除会更隐蔽。
- 实测案例：删除 03 章后，残留包括「3.1 散点图剔除了…」「3.3 与 3.4 的集中度」「远低于 A 类的 82.9%」「共 5 章 · 15 张图表」。
- 做法：
  1. 章节重编号（04→03、05→04）后，**同步改**：`sec-tag`、`h2/h3` 编号、结论卡证据行、附录口径编号、页脚章数/图表数；
  2. 删完跑一遍**关键词残留扫描**：把被删章节的所有小标题名 + 唯一数字（如 `17.4×`、`−24.2%`、`39.1%`）逐个 grep，命中数必须为 0；
  3. 图表容器 id 与 `mk()` 配置**不必跟着重编号**（id 是内部标识），但容器集合与配置集合必须**完全相等**——这条由构建脚本自动断言。
  4. 每张图的 insight 里，**凡引用被删图表数字的句子必须同步改写或删除**——最好的自检是逐条问「这句话的数字，现在还有哪张图/哪张表能溯源」。
  5. **新增了指标就要进附录公式表**：实测案例——给「二级分类明细表」加过两列衍生指标（老品同比、新品占比）后，附录公式表必须同步补上定义行，否则读者无法复算。**反向同理：删列时附录公式表里对应的定义行必须一并删掉**，否则读者会去找一个不存在的列。
  6. **新增一张图是删除的镜像操作，检查清单相同但更易漏**——实测案例：在 03 章第 3 位后插入「铺货密度」图（编号 3.4）后，需要同步的有：① 页脚「共 4 章 · **14** 张图表」的计数；② 该章后续编号顺延（明细表 3.4 → 3.5）；③ 附录里指向被顺延编号的引用（口径①「3.4 的在售 ASIN」→「3.4 铺货密度图与 3.5 明细表的…」、口径③「3.4 的「在售 ASIN」」→ 3.5）；④ 新容器 `id` 与 `mk()` 配置**必须同时加**（构建脚本断言两集合相等）；⑤ 新卡片若不是本章最后一张，**必须带 `mb-6`**（否则与下卡粘连，构建脚本断言）；⑥ 新 insight 里每个数字都要能复算。
  7. **「移动小节」比「增删」多一层风险：编号重排会产生交叉覆盖**——实测案例：把第 7 位的小节（明细表）上移到第 4 位之后，顺延后同时存在 `3.5→3.6` 与 `3.7→3.5` 两条映射。**分步 `replace('3.5','3.6')` 再 `replace('3.7','3.5')` 会互相污染**（第一步产出的新 `3.6` 会被后续步骤再次改动）。做法：
     - 替换锚点**必须带足上下文**（用 `'3.5 B1 专项：儿童款 vs 非儿童款'` 这种完整标题串，而不是裸编号 `3.5`），每条 `assert count==1`；
     - 卡片块的提取/插入用**标签配平扫描**（从卡片 `<div` 起逐个匹配 `<div`/`</div>` 至深度归零），不要用 `find('</section>')` 向后找边界；
     - **`mb-6` 要跟着换位**：移入中间的要补上，变成本章末张的要删掉；
     - 顺带做一次**旧编号残留全扫**（`3.7 八个二级`、`3.5 B1 专项`、`3.7 明细表`、`与 2.2、3.7 同口径`… 命中必须为 0）；
     - **意外收获**：历史漏网的旧编号可能被这次移动顺带修正（实测：附录口径③里残留的「3.4 与 3.5」，移动后 `3.5` 恰好重新指向明细表，自动变正确）——**改前先判断这类引用是该改还是该留**，别机械替换。

**G12 删章节时，被删章节支撑的结论是否已迁移或作废？**

- 章节删掉 ≠ 结论作废。原挂在被删章节上的判断（如"头部 20 款占 63.3%"）要么另找图表承接，要么改写措辞。
- 做法：删完逐条问「这个数字现在还有图能溯源吗」。没有就二选一：迁移到保留的图表（例如把 A 类整体参考曲线并入新的集中度图）、或改为不依赖图表的定性表述并在 `src` 行注明数据出处。
- **实测案例：章节导语本身也常是"被删章节的支撑物"**。删掉 01 章的「1.3 A 类季节性」后，01 章导语里仍写着「**更关键的是**节奏差异：A 的销量高度集中在 6~7 月」——这句正是被删那节的核心结论。处理：① 引导词「更关键的是」降级为「此外」（不再暗示后面有专章展开）；② 补指向「（见 1.1 走势）」，但**必须先复算确认替代图真的看得出该特征**（实测 A 类 24 个月里 2025 与 2026 两个 6~7 月都是局部高点、达相邻月均值的 2.4~2.9 倍，1.1 图确实可见），不能想当然挂一个"见 X 图"。
- **同类漏网：h2 / 章节大标题**。实测本例删章节时发现 01 章 h2 仍写着「和一个**跑快 5 倍**的小切口」，与上一轮刚修正的导语（「只看老品，存量盘仅 +1.4%」）自相矛盾——典型的"改了正文漏了标题"。**凡动过导语里的核心数字，回头必查同章的 h2 与 sec-tag。**
- **第三张图：同一张卡片内删一图时，h3 的「分工说明」会失效。** 实测案例——2.6 卡片标题原为「2.6 评分：整体 4.03…<span class="src">(上：评分档分布；下：各形态均分，横轴截断在 3.5–4.5…)</span>」，删掉上方的「评分档分布」后，`上：/下：` 的分工描述直接说错。**凡 h3 里写了几张图各自的角色（上/下、左/右、①②③），删图后必须改写这段而不是只删容器。**
- **处理被删图数字的三条路，而不是两条**：① 迁移到保留图表；② 降级为定性表述；**③ 保留数字 + 在 `src` 补全它的计算口径**（适用于该数字仍有决策价值、且与保留图表同源的情况）。实测本例选 ③——被删的「评分档分布」数字（`28.6% 低于 4.0`、`头带 ≥4.5 占 20.5%`、`冰环 <4.0 占 33.7%`）与保留的均分图同出 K 列评分，于是在 `src` 追加「档位占比 = 组内评分落在该档的 ASIN 数 ÷ 该组有评分 ASIN 数（档位：<4.0 / 4.0–4.3 / 4.3–4.5 / ≥4.5）」。**关键：走 ③ 必须回到源数据复算一遍这些数字**（本例 28.64%→28.6%、20.55%→20.5%、33.66%→33.7% 全部吻合），不能因为"图已经删了"就默认旧值还对。

**G13 衍生指标命名：别借行业黑话；同源指标不要并列成多列**

- **命名必须词义自明。** 实测案例——从零售业借来的「同店同比」（same-store sales）被用户直接质疑「这是什么玩意」。该词预设读者知道"门店"这一层，可报告里根本没有"店"，只有 ASIN；「同店 + 同比」两个词叠在一起、没一个字被解释过，表头只能靠猜。
- **做法：优先用报告里已经出现过、且已被 `src` 口径注解释过的词去配对。** 本例中「新品占比」先立住了，"新品 / 老品" 就是一对自解释的词 → 改名「**老品同比**」，读者无需任何背景知识。同理应避开的黑话：可比同比、存量同比、铺货率、动销率。
- **同源冗余检测：两个指标若分子相同、只有分母不同，就是同一事实的两次表述，不要并列成多列。** 实测恒等式：
  `新品占比 =（销量同比 − 老品同比）÷（1 + 销量同比）`
  三列并排（销量同比 / 老品同比 / 新品占比，实测推算与表中值逐行吻合到 0.1pp）逼读者自己做减法；砍到两列即可完全推出第三列。
- **自查三问：** ① 表头每个词，是否都能在 `src` 口径注里找到它**自己**的定义行？② 任意两列能否互相推导（能推 = 冗余，应合并）？③ 是否还有大量"XX 口径""XX 率"这类**没说清主体**的术语？
- **落地：删列 / 改名要同步五处**——① 表头数组 ② 行映射（删单元格，注意末项 `]` 前不能留逗号）③ `src` 口径注 ④ 图表 insight 文案 ⑤ 附录公式表。改完做**残留扫描**：旧词全文出现次数必须为 0，且被删列引用的**数字**（如本例 `26.5%`）也要全文 grep 归零。
- **注意 `build_data.py` 里的内部字段名（如 `yv_lfl` / `zvs`）在 data.json 里保留无害**——读者看不到，不必为改名去动数据层代码，避免误伤已核对过的数据口径。

**G14 口径变更（换分母 / 换分组）是「批量改名」的加强版：多查 5 类检查点**

- 触发：用户要求统一某个口径，例如「报告中所有的均销量都要取单月销量 > 0 的有数据的 ASIN」。
- **必查 10 处**（G13 的改名只涉及 5 处，口径变更多出 5 处）：
  1. 计算函数里的分母（`f.vti / f.n / 12` → `f.na`）；
  2. **图内系列的数据取值**——柱/线直接 map 的字段（`data:D.form.map(f=>f.n)` → `f.na`）。**只改分母不改柱子，图内会自相矛盾**：读者拿柱值算不出线值；
  3. 轴名 / 图例名（`name:'ASIN 数'` → `'在售 ASIN 数'`，本例 3 处）；
  4. 卡片 `h3` 标题；
  5. insight 文案里的**每一个数字**（本例 `317/207/123 件`、`2.6 倍` → `327/221/129 件`、`2.5 倍`，共 4 个数）；
  6. `src` 口径注；
  7. 附录公式表里的定义行；
  8. **结论卡里引用的同一组数字**——实测这组数同时出现在 2.2 insight 和结论卡② 里，最容易只改一处；
  9. **tooltip 的取数与标签**——tooltip 里的「ASIN 数」若仍是总数口径，读者拿它验算均产会算不通；改成「在售 ASIN 数：X（全部 Y）」既统一口径又不丢信息；
  10. 附录口径说明——补一句「本报告所有「均销量」类指标一律以「近 12 月销量 > 0 的在售 ASIN」为分母，另有 N 个零销量 ASIN 不计入」。
- **残留扫描必须防假阳性**：检测「还有没有 `f.n` 作分母」时，写 `"/ f.n /" in src` 会被 `"/ f.na /"` **前缀匹配**（`na` 以 `n` 开头）而误报。必须加词边界：`re.search(r"/\s*f\.n\s*(/|\)|;|,)", src)`。同类会互相污染的字段名还有 `f.n`/`f.na`、`yr`/`yr_lfl`、`yv`/`yv_lfl`。
- 旧数字扫描：`317`、`2.6 倍`、`79 个 ASIN` 全文出现次数必须归零。

**G15 源表结构变更（分组合并 / 新增维度）比换口径影响更广：基数字要全链重算**

- 触发：用户在报告交付后改动源表，例如「冷敷手套·袜并入 B3」「B1 新增『是否儿童』形态列」「B3 形态细分为 7 个部位」。这类改动会让**分组基数变化**（实测 B 类二级分类 **9 个 → 8 个**）。
- **必查 8 处**：
  1. 数据层脚本（换快照源、新增聚合分支，如本例加 `b1kid` / `b3form`）；
  2. **章节大标题里的基数词** —— 实测案例：正文各处都改成了"八个二级"，唯独 03 章大标题「B 类**九个**二级：量在敷包，钱在冷疗机」漏改，而它恰是全章最显眼的位置；
  3. 章节导语里**前提性描述**（"该级未划分形态"这类话会因新增维度而失效，须改写）；
  4. 每张图的 insight 数字与图标题；
  5. 图配置本身（分组增减、**视觉编码变更**）；
  6. `src` 口径注 —— **删掉某种视觉编码时，解释它的那句话也要删**：实测去掉 Treemap 色深后，src 里"色深档位按均价分三档（<$18 / $18–40 / ≥$40）"必须同步清掉，否则读者按图找不到色深；
  7. 附录公式表 + 口径说明里的编号引用；
  8. 页脚「共 N 章 · M 张图表」的 M。
- **⚠️ 残留扫描必须同时覆盖中文数字与阿拉伯数字**：分组数 9→8 时，搜 `"9 个二级"` **查不到**写作「九个二级」的那一处（实测漏网就发生在这里）。正确写法：
  `for kw in ("九个二级","九类","9 个二级","9 类"): assert plain.count(kw)==0`
- 删改视觉编码（色深、象限分色、图例）后，**图里的 legend / 分色逻辑与正文解释要一起删**，否则会留下"图例说有四种颜色、实际只有一种"的矛盾。实测：3.2 气泡图去掉象限注释时，需同时删掉 `QUAD` 分色数组、`legend`、统一 `itemStyle.color`，并把 `grid.top` 从 52 调回 34（legend 占位消失）。
- **⚠️ 「几项合计占 X%」必须回到原始分子分母重算，不能用已四舍五入的份额相加**。实测案例：三个部位份额 `31.9% + 29.7% + 28.1%` 表面等于 **89.7%**，但用原始销量算精确值是 **89.83% → 89.8%**——差 0.1pp，肉眼和心算都发现不了，靠断言才抓到。写法：`exact = sum(vi for 目标项)/sum(全部) * 100`，再 `round(exact,1)` 写入文案；构建后把每个百分比当断言复算一遍。

**G16 报告会「自证其伪」吗？——单看每章都对、通读才发现的三类问题**

- 数字全部复算正确 ≠ 报告站得住。以下是**只在整体通读时才会现形**的三类硬伤（任一单章看都正常）：
  1. **同一数字在报告首尾承担相反角色**。实测案例：`+16.9%` 同时出现在 HERO KPI（绿色正向）、01 章导语（「是 B 的 5 倍」，用来证明"A 跑得快"）、附录②与结论卡①（「剔除新品后仅 +1.4%」，用来否定它）。读者在前 1/3 建立"A 高速增长"的印象，读到结尾被推翻。
     做法：把**被后文否定的数字**全部列出来，检查它在被否定之前是否曾被当作正面论据；若是，要么前置限定词，要么换成不冲突的数字。
  2. **章节导语承诺的问题当页没答**。实测案例：04 章导语写「进哪条线、选哪个形态、从哪条缝隙切入」，三张结论卡全是事实陈述，无一条给出"动作 + 前提 + 风险"。
     做法：把导语里每个问句当**验收项**，逐条在正文找答案；答不了就删问句或补答案。
  3. **数据层备而未用**。实测案例：`data.json` 有 23 个顶层键，报告只用了 12 个；未用的 11 个里含**三个最关键的决策变量**（价格带效率 / 头部 20 画像 / 新品存活率），且已算出「$20–30 档效率指数 288，是 $10–15 档的 3.2 倍」这种可直接指导定价的结论。
     做法：加一条**覆盖度检查**，打印未使用的数据键并逐项人工确认"有意不用还是漏了"：
     ```python
     used=set(re.findall(r"D\.([a-zA-Z0-9_]+)", charts_src))
     print("未使用：", [k for k in data_json if k not in used])   # 不许默认忽略
     ```
- **跨分组取同名 TOP N 之前，先对齐基数**。实测案例：2.5「TOP20 累计份额」围巾 96.2% / 头带 85.3% / 冰环 77.9%，看着"围巾最寡头"；但三者**在售 ASIN 数分别是 44 / 75 / 98**——TOP20 已覆盖围巾 45% 的样本、冰环仅 20%。基数差一倍以上时，同一 N 的累计份额不可直接排序。
  做法：insight 必须带上各组基数，或改用**等比例分位**（TOP 10% / TOP 25%）替代固定 N。
- **峰谷比要限定在同一周期内**。实测案例：用 24 个月口径取「谷 2025-01 / 峰 2026-06」，跨了 17 个月，把**同比增长混进了季节性落差**（得 2.8% / 5.5% / 9.2%）；改用近 12 个月同周期口径则为 3.7% / 7.6% / 12.0%。且 `src` 里没写用的是哪个口径。
  做法：峰与谷必须落在同一个 12 月窗口内，并在 `src` 注明「近 12 月」还是「24 个月」。
- **同一指标只允许一个名字**。实测案例：同一个"近 12 月销量 ÷ 在售 ASIN 数 ÷ 12"在报告里有 4 个叫法——`单品月均产`(18 次，ch6/ch23 轴名) / `单 ASIN 月销量`(8 次，ch21 轴名) / `单ASIN月销量`(1 次，3.5 表列名) / `单品月产`(3 次)。同名分组也会漂移：源表字段值是 `头带/面罩`，正文 12 处全写 `头带·面罩`，**图上显示斜杠版、文字写间隔号版**。
  做法：定一个规范名，用脚本统计全文各变体出现次数（`for kw in 变体: print(kw, plain.count(kw))`），逐个改到 0（表列名受宽度限制时可缩，但必须与轴名同源且 `src` 里点明等同）。
- **精简 insight 时，被删掉的往往是限定条件**。实测案例：把某节从 733 字砍到 165 字，顺带删掉"样本仅 23 个，不宜据此判断"这句限定，使"评分差异极小"从**有保留的结论**变成**无条件结论**。
  做法：取舍标准是「删推导过程、留限定条件」——**样本量、异常值、口径边界是结论的一部分，不是冗余**。

**G17 「近 12 月」口径下有没有被单月异常值污染？**

- 汇总口径（Σ近 12 月）会把**任意一个月的异常尖峰**放大进整组的同比、份额、单产里，而它表面上完全正常——不报错、无缺口，只是某个数偏大。
- 实测案例：B5 头部冰帽 2025-12 单月 39.2 万件，占该二级近 12 月销量的 **20.3%**，由 TheraICE 两个 ASIN 同期各约 12 万件贡献（这两个 ASIN 在前后月份仅约 4 万件，尖峰是常态的 **3 倍**）。该月已计入全部「近 12 月」口径，导致 B5 的三项读数同时被抬高：同比 −0.8%（**把该月替换为前后月均值则为 −12%**）、量份额 15.8%、单品月均产 1,518 件。
- 做法：
  1. 每个分组先画/扫一遍 **逐月序列**（走势图本来就有）——`峰值月 ÷ 相邻两月均值 > 2` 即为可疑尖刺；
     ```python
     for f in groups:
         mv=f["mv"]; mx=max(range(len(mv)), key=lambda i: mv[i])
         if mx in (0, len(mv)-1): continue
         nb=(mv[mx-1]+mv[mx+1])/2
         if nb and mv[mx]/nb > 2:
             print("异常尖峰:", f["name"], months[mx], mv[mx], "%.1f×"%(mv[mx]/nb))
     ```
  2. 定位到具体 ASIN（按该月销量降序取前几名），判断是真实促销 / B2B 大单还是数据问题；
  3. **不要静默剔除**——在附录加一条「单月异常值」口径说明：尖峰月份、来源 ASIN、占该组比重、影响哪些指标，并给出「若替换为前后月均值则为 X」的敏感性数字，让读者自行取舍。
- ⚠️ 这一步极易被跳过：**常规复算脚本（分组求和逐项对比）发现不了它**，只有在逐月走势里才会露头。年度同比、份额、均产三项都会被同一个尖峰同时污染，属于"一处异常、多处失真"。

**G18 改「用户磁盘上的成品 HTML」前，先判断它与构建链是什么关系**

- 场景：用户把报告复制到桌面 / 项目目录外（常命名为 `…报告1.html`、`…_副本.html`），然后要求改其中某段文案。**此时绝不能"改源片段再重建"** —— 那份副本很可能已经分叉（用户在副本上直接改过、或它取自更早的一次构建），重建会把副本独有的内容全部冲掉。
- 判断顺序：
  1. 先 `difflib.unified_diff(副本, 构建产物)` 看**谁更新、副本有哪些独有行**（`-` 行 = 副本独有，`+` 行 = 产物独有）；若副本的独有行全是"产物那行的短版本"，说明副本是旧分支。
  2. 同时留意同名 `…_副本.html` —— 先比对 md5，若与主文件字节相同，它是用户的手工备份，**不要一起改**（除非用户明说）。
  3. 确认是分叉副本 → **原地改 + `cp` 出 `.bak` + 出现次数断言**，改完做结构校验：`<div>` 配平、图表/表格容器数、`<script>` 配平，并把所有内联 `<script>` 抽出来逐个 `node --check`。
- **影子构建（零副作用验同步）**：想知道"源片段和已构建产物是否还一致"，不要直接跑构建（会覆盖产物）。做法是把 `build_report.py`、`runtime_check.js`、`output/{report_body.html,report_charts.js,data.json}` 复制到 `/tmp/<proj>/`，把脚本里的 `BASE` 常量改写为该临时目录再执行，最后 `filecmp.cmp(shadow_out, real_out, shallow=False)` 字节比对。实测用这一招同时查出了三件事：① 用户桌面那份是旧分支（少 1 张结论卡、缺「适用范围」段与各处「口径提示」、无 `【A 类】/【B 类对照盘】` 前缀）；② 工作区 sources 有一处**改而未构建**（3.2 的 insight 被加长了）；③ 该次构建**会失败**。
- **⚠️ 「先写文件、后跑自检」的构建脚本：自检失败 ≠ 产物没变。** 本项目 `build_report.py` 是 `open(OUT,"w").write(html)` 之后才跑 `errs` 检查，失败时 `sys.exit(1)` —— 但**产物早已被覆盖**。实测后果：一次自检失败（2 条 insight 超 180 字门禁）留下了"看起来构建成功、其实没通过校验"的 HTML，会话结束前没人发现。做法：① 构建脚本改成"先自检、后写盘"（把 `write` 移到 `errs` 判断之后）；② 在自检失败时显式打印"产物已更新但未通过校验，请勿发布"；③ 若暂时不改脚本，看到非 0 退出码必须回头确认产物是否已被覆盖。

**G19 构建脚本的外部依赖要「自动探测」，不要硬编码版本目录；派生字段先做「披露率体检」**

- **硬编码的运行时路径会随环境升级失效。** 实测：`build_report.py` 里写死 `NODE = ".../node/versions/22.22.2-3/bin/node"`，环境把版本目录换成 `22.22.2-6` 后，构建在 `subprocess.run` 处直接抛 `FileNotFoundError`，**而"写出 HTML"这一步已经成功**，于是留下一个"文件写了、自检没跑"的半成品。修法（已用于 `build_kitset.py`）：
  ```python
  import glob, os
  def _find_node():
      for c in sorted(glob.glob(os.path.expanduser("~/.workbuddy/binaries/node/versions/*/bin/node")), reverse=True):
          if os.path.exists(c):
              return c
      return "node"
  NODE = _find_node()
  ```
  同理适用于 python 解释器、模板路径、技能目录 —— 凡带版本号或用户名的绝对路径，都应探测 + 兜底，而不是写死。
- **从五点/描述里解析出的结构化字段，先算"披露率"再决定能不能当指标。** 实测：想给"跨部位套装"加「凝胶袋总数」这一列用于算"每袋单价"，解析后发现**只有 20.7%（6 / 29）的竞品在五点里写了数量**，其余只写 "gel packs included"。此时正确做法是**把这一列降级为"文案披露率"的观察项**（结论变成"本类目配置披露度低"），而不是硬报一个由 21% 样本外推的平均值。判断标准：披露率 < 60% 的字段不做均值类指标，只做分布/提及率。
- **反过来说，解析前一定先抽样看原始文本的写法。** 实测同一条五点里同时出现阿拉伯数字（"4 gel pack"）与英文数词（"six gel ice packs"），只写一种正则必然漏。先 dump 20 条原句再写规则，能省掉一轮返工。

**G20 用户已经手工维护了分类列时，程序口径应「从属」而不是「并行」**
- 实测案例：某专项分析最初用「标题含 ≥2 个部位组」的程序规则圈选对象，得到 29 个；后来用户把源表形态列**手工标注**好了（23 个，并明确命名），程序口径仍会得到 27 个——多出的 4 个是「冷帽+颈罩」组合（不含手套与袜，**属另一品类**），而且这 4 个同比 −40.8%，**直接导致同一批数据被读成两种相反结论**（+30.7% vs +8.6%）。
- 判断顺序：① 先问「这个口径是**替代**人工标注，还是**补充**？」② 若人工标注已能覆盖（本例中切碎问题已被手工标注修好），程序口径就该退出，最多在附录里作为「对照口径」旁注一句差异与原因；③ **绝不要让两个口径并行产出正文结论**。
- 旁注要写清三件事：程序口径会得到几个、多/少的是哪些、为什么不算（本例：「会得到 27 个，多出的 4 个是 Cold Cap and Neck Wrap，不含手套与袜，与本报告对象非同品类，故不纳入」）。
- 推论：**用户手工标注的列是"权威源"，程序规则是"辅助"**。反过来做（用程序规则覆盖人工标注）会让报告与用户对不上——他会直接问「我标的是 23，你为什么算 27」。

**G21 交付前数字断言的写法：注意"纯文本"与"含标签"两个语境**
- 把 HTML 去标签后得到纯文本 `P`，此时 `"<b>89.5%</b>" in P` **必然为假**（标签已被剥掉），会误报成"数字缺失"。实测一口气误报 4 项，白排查一轮。
- 正确写法：**含标签的断言查原 HTML，纯文本断言查 `P`**；数值断言不要用 `==`（`44.210417…` 与 `44.21` 不等），用 `abs(v-target) < 0.05`。
- 同类的还有「残留扫描被同值误伤」：`33.7%` / `15.8%` 这类数字在同一份报告里可能既是被改项（B 类份额）、又是无关项（A 类某形态评分占比）——**残留扫描必须带上下文，或先确认该数字的全部出处**，否则会把"不该改的"一起改掉。
- 一句话：**改之前先列出该数字的每一处出处并分类，改之后用"剩余出处 = 预期出处"来验收**，而不是只数总数。
